# Use-case modules

One runnable module per thing you would do with Runpod, each a complete
configuration with variables, outputs, a README, and a pinned provider
requirement. They double as the acceptance tests: `tests/*.tftest.hcl`
applies them with output assertions, and `task validate-tf` fails when a
registered resource or data source is used by none of them.

| Module | What it does | Cost |
|---|---|---|
| [gpu-pod](gpu-pod/) | One GPU pod from an image or template, optional network volume | Per hour while it runs |
| [cpu-pod](cpu-pod/) | One CPU-only pod | Per hour while it runs |
| [serverless-endpoint](serverless-endpoint/) | GPU Serverless endpoint plus its workers, builds and releases | Only under load |
| [serverless-endpoint-cpu](serverless-endpoint-cpu/) | CPU Serverless endpoint | Only under load |
| [template](template/) | Reusable pod / endpoint template, read back and listed | Free |
| [network-volume](network-volume/) | Persistent network storage, listed | For allocated storage |
| [registry](registry/) | Registry credentials, optional ECR pull delegation, listings | Free |
| [cluster](cluster/) | Multi-node GPU cluster, read back with its member pods | Per hour for every member pod |
| [account-ssh-keys](account-ssh-keys/) | The account's SSH public keys | Free |
| [pod-lifecycle](pod-lifecycle/) | Start / stop / restart / terminate an existing pod, read it back | Changes what the pod costs |
| [catalog-discovery](catalog-discovery/) | GPU, CPU, data center and public template catalogs | Free |
| [billing-report](billing-report/) | Time-bucketed spend per resource kind | Free |
| [logs](logs/) | Bounded reads of a pod's or a worker's log stream | Free |
| [legacy](legacy/) | Deprecated GraphQL / REST v1 shims: machines, account, 1.x billing | Free unless a machine is registered |

Every module pins `runpod/runpod` to `~> 2.0` in its `versions.tf`.
Documentation snippets for the registry pages live under
`examples/resources/` and `examples/data-sources/` and are not modules.

## Running a module

The modules resolve the provider from a local build, so build it once from the
`v2/` directory:

```bash
task build   # local filesystem mirror + artifacts/dev.tfrc
export RUNPOD_API_KEY=...
```

Then, from the module directory:

```bash
export TF_CLI_CONFIG_FILE=../../artifacts/dev.tfrc
terraform init
terraform apply
terraform destroy   # for the modules that create something
```

Against the published provider, leave `TF_CLI_CONFIG_FILE` unset: the
`source = "runpod/runpod"` in each module's `versions.tf` then resolves from the
registry. Each module pins the release its guide documents: an exact pin while
that release is a candidate, `~> MAJOR.MINOR` from the final release on. The
pin comes from `RELEASE` in the Taskfile and `task docs` rewrites it.

## Using a module from your own configuration

```hcl
module "training_pod" {
  source = "github.com/runpod/terraform-provider-runpod//v2/modules/gpu-pod?ref=v2.0.0-rc.3"

  name        = "training"
  gpu_type_id = "NVIDIA GeForce RTX 4090"
  disk        = 50
}
```

Pin `ref` to the release you use. The modules will be published to the
Terraform Registry as separate `terraform-runpod-<name>` repositories later;
the in-repository path is the source until then.

## Inputs that have no default

`registry` needs a real login (`username`, `password`) and, for the ECR
delegation, an ARN; `account-ssh-keys` needs the complete `keys` set;
`pod-lifecycle` needs a `pod_id`. Each README gives the exact `-var`
arguments.

## Module READMEs

The tables in each README between the `BEGIN_TF_DOCS` / `END_TF_DOCS`
markers are generated by terraform-docs from the module's own files.
`task docs` refreshes them, and `task validate-tf` fails when they are stale.
Edit the prose above the markers by hand and the variable / output
descriptions in the `.tf` files.
